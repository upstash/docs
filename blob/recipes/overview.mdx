---
title: "Recipes"
---

Each recipe is one feature wired end to end: the handler, the route, the component, the page that renders the result, and the delete. The choices are made and explained, so you can copy one, rename the paths, and have it work.

Pick by the shape of the data:

| Recipe | Bucket | Objects per row | Written by | Path |
| --- | --- | --- | --- | --- |
| [Profile pictures](/blob/recipes/avatars) | public | one, overwritten | browser | stable, served through `versionedUrl` |
| [Product images](/blob/recipes/product-images) | public | many, ordered | browser | `uniquePath` |
| [Site assets and CMS media](/blob/recipes/site-assets) | public | one per file | browser and a build script | `uniquePath`, or versioned filenames |
| [AI-generated images](/blob/recipes/ai-images) | public | one per generation | your server | new path per generation |
| [File attachments](/blob/recipes/attachments) | public | many per thread | browser, multipart | `uniquePath` |
| [Video uploads](/blob/recipes/video) | public | one, multi-gigabyte | browser, multipart | `uniquePath` |
| [Private documents](/blob/recipes/private-documents) | private | one per document | both | stable for generated files, `uniquePath` for uploads |
| [Generated exports](/blob/recipes/exports) | private | one, expiring | a background job | new path per export |

Two rules run under every one of them. Your database is the index and the bucket only holds the bytes, so every page reads a row rather than listing the bucket. And a path is either unique per upload or overwritten on purpose, never both; [Caching](/blob/bucket/caching) explains what each choice lets you cache.

If you have not created a bucket yet, start with the [Quickstart](/blob/overall/quickstart).
