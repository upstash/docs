Most agents only act when someone messages them. [MCP Events](https://github.com/modelcontextprotocol/experimental-ext-triggers-events)
lets an agent wait for something instead: the host subscribes to an event on your MCP server, and
when it happens your server POSTs a signed webhook that wakes the agent up.

`@upstash/mcp-toolkit/events` implements the server side. You define events with typed payloads and
call `emit` when something happens. The toolkit handles subscriptions, callback verification,
signing and retries: subscriptions live in Upstash Redis, and every delivery goes through
[QStash](/qstash/overall/getstarted), which retries failed webhooks with backoff.

<Note>
  MCP Events is a draft. As of October 2026, ChatGPT is the host that subscribes to it (webhook
  delivery, in Work chats), following [OpenAI's MCP Events guide](https://developers.openai.com/plugins/build/mcp-events).
  Claude Code, Cursor and OpenCode don't subscribe yet.
</Note>

```bash
npm install @upstash/mcp-toolkit @modelcontextprotocol/server @upstash/redis @upstash/qstash zod
```

## Quickstart

Three files in a Next.js app.

### 1. Define the event layer and your events

```ts lib/events.ts
import { createEventLayer, QStashDelivery, RedisSubscriptionStore } from "@upstash/mcp-toolkit/events";
import * as z from "zod";

export const events = createEventLayer({
  store: new RedisSubscriptionStore(),
  delivery: new QStashDelivery({ url: `${process.env.APP_URL}/api/events` }),
  // Encrypts the hosts' signing secrets at rest. Generate with: openssl rand -base64 32
  secretKey: process.env.MCP_EVENTS_SECRET_KEY,
  // Who is calling. `auth` is the verified token your MCP route passes to the SDK; see
  // "Users" in the MCP Tasks docs for how it's populated.
  principal: ({ auth }) => auth?.extra?.userId as string | undefined,
});

export const commentCreated = events.define("comment.created", {
  description: "A new review comment was added to a document.",
  // What a subscriber filters on.
  input: z.object({ documentId: z.string() }),
  // What every delivery carries.
  payload: z.object({ documentId: z.string(), commentId: z.string(), text: z.string() }),
  // Required: who may subscribe with these arguments and receive what they match.
  // Runs on every subscribe and refresh, and again before every delivery.
  authorize: (args, { principal }) => canRead(principal, args.documentId),
});
```

### 2. Register the events on your MCP server

```ts lib/server.ts
import { McpServer } from "@modelcontextprotocol/server";
import { events } from "./events";

export function createServer() {
  const server = new McpServer({ name: "docs", version: "1.0.0" });
  // Adds events/list, events/subscribe and events/unsubscribe next to your tools.
  events.register(server);
  return server;
}
```

Serve it with `createMcpHandler(() => createServer())` as usual. Nothing else changes on the MCP
endpoint.

### 3. Add the delivery endpoint

```ts app/api/events/route.ts
import { events } from "../../../lib/events";

export const POST = events.createDeliveryHandler();
```

QStash delivers each event here. The handler verifies the QStash signature, signs the envelope
with the subscriber's secret, POSTs it to the host, and answers `500` when the host's callback
failed so QStash retries. A bad signature or body gets `489` with `Upstash-NonRetryable-Error: true`.

### Emit

Call `emit` wherever the change happens: a route, a webhook from your own app, a background job.

```ts
await commentCreated.emit({ documentId: "doc_123", commentId: "c_9", text: "Ship it?" });
```

`emit` is typed by the `payload` schema and validates against it. It reaches every subscription
whose arguments match (everyone watching `doc_123`), checks `authorize` again for each subscriber
before delivering, and returns the event id and how many subscriptions matched.

### Environment variables

```bash .env
UPSTASH_REDIS_REST_URL=...
UPSTASH_REDIS_REST_TOKEN=...
QSTASH_TOKEN=...
QSTASH_CURRENT_SIGNING_KEY=...
QSTASH_NEXT_SIGNING_KEY=...
# Encrypts the hosts' signing secrets at rest. Generate with: openssl rand -base64 32
MCP_EVENTS_SECRET_KEY=...
# Where QStash delivers events. Must be publicly reachable.
APP_URL=https://your-app.vercel.app
```

## What happens on the wire

1. The host calls `events/subscribe` with the event name, arguments, its callback URL and a
   `whsec_` signing secret.
2. For a new callback or secret, your server POSTs a signed verification challenge and requires it
   echoed back, then stores the subscription and answers with its `id` and a `refreshBefore` time.
3. When you `emit`, every matching subscription that `authorize` still allows gets a POST with the event envelope and
   [Standard Webhooks](https://www.standardwebhooks.com/) headers:

```json
{
  "eventId": "evt_7c1…",
  "name": "comment.created",
  "timestamp": "2026-10-07T12:05:00Z",
  "data": { "documentId": "doc_123", "commentId": "c_9", "text": "Ship it?" },
  "cursor": null
}
```

The event id stays the same across retries, so the host can drop duplicates. The signature is
computed fresh on every attempt.

## Matching

A subscription matches when every argument it gave equals the emitted value. Emitting
`{ repo: "a", branch: "main" }` reaches subscribers of `{ repo: "a" }`, of
`{ repo: "a", branch: "main" }`, and of `{}`.

The values come from the payload fields named in the input schema, so when the payload carries
every input field, `emit(payload)` needs nothing else. When it doesn't, the type of `emit` makes
`args` required, and an emit with no value for a required input field throws, so a filter can never
silently match nothing:

```ts
const replyPosted = events.define("reply.posted", {
  description: "A reply was posted in a thread.",
  input: z.object({ threadId: z.string() }),
  payload: z.object({ text: z.string() }), // no threadId here
  authorize: (args, { principal }) => canReadThread(principal, args.threadId),
});

await replyPosted.emit({ text: "Agreed" }, { args: { threadId } }); // `args` is required
```

Other options:

```ts
await commentCreated.emit(payload, {
  to: ["alice", "carol"], // only these users' subscriptions; optional
  eventId: comment.id, // emitting the same id twice is deduplicated
});
```

For conditions that exact matching can't express, add `match: (args, payload) => boolean` to the
event definition.

## Users and subscriptions

Three things decide who gets an event: the callback URL says **where** it goes, the subscription's
arguments say **what**, and `authorize` says **who may**.

**The host routes to its user.** Every subscription carries a callback URL and signing secret that
the host generated for it. ChatGPT, for example, sends a unique
`https://connectors.api.openai.com/webhook/mcp-events/<id>` per monitor. Posting to that URL
reaches the right user's agent, so your server never needs to know who the host user is. Two users
subscribing to the same event produce two subscriptions and two deliveries.

**Your server knows who subscribed.** `events/subscribe` arrives with the same auth as any other MCP
request: the `AuthInfo` your route verified and passed to `handler.fetch(request, { authInfo })`
(see [Users](/redis/sdks/agentkit/mcp-tasks#users)). `principal({ auth, request })` turns it into
the subscriber's id, which is stored on the subscription and becomes part of its id.

**`authorize` decides who may, and keeps deciding.** It is required, and runs twice:

| When | What it gets |
| --- | --- |
| Every subscribe and refresh | `args`, `{ principal, context, phase: "subscribe", auth, request }` |
| Before every delivery | `args`, `{ principal, context, phase: "deliver" }` |

The token is never stored, so there is no `auth` or `request` behind a delivery. The second check is
what stops events when someone loses access after subscribing; a delivery it refuses is dropped, not
retried. An event any authenticated caller may hear says so with `authorize: () => true`.

**Context for the delivery check.** Return `{ id, context }` from `principal` instead of a string
to store small, non-secret data (an org id, a role) with the subscription. `authorize` gets it back
as `context`:

```ts
const events = createEventLayer({
  store,
  delivery,
  principal: ({ auth }) => ({
    id: auth?.extra?.userId as string,
    context: { orgId: auth?.extra?.orgId }, // never the token
  }),
});

const memoPosted = events.define("memo.posted", {
  description: "A memo was posted to your org.",
  input: z.object({ orgId: z.string() }),
  payload: z.object({ orgId: z.string(), text: z.string() }),
  authorize: (args, { context }) => context.orgId === args.orgId,
});
```

`context` is a snapshot from subscribe time, capped at 4 KB. For revocation, check your own data
with `principal` rather than trusting the snapshot.

**Personal events use `to`.** Some events belong to one user, like "your export finished". Mark them
`personal: true`, and every `emit` must name the user with `to`; the type requires it, and so does
a runtime check. A subscription with no arguments then only hears about its own user's events:

```ts
const exportFinished = events.define("export.finished", {
  description: "Your export finished.",
  payload: z.object({ exportId: z.string(), url: z.string() }),
  personal: true,
  authorize: () => true, // `to` already limits it to the export's owner
});

await exportFinished.emit({ exportId, url }, { to: userId });
```

Unsubscribing recomputes the id from the caller's principal, so only the subscriber can remove a
subscription.

<Note>
  `principal` is required, and there are no anonymous subscriptions: when it returns `undefined`,
  subscribe and unsubscribe are refused with reason `not_authenticated`, before any challenge is
  sent. A server with no users of its own passes `principal: () => "local"`.
</Note>

## Task finished events

If you use [MCP Tasks](/redis/sdks/agentkit/mcp-tasks), a `task.finished` event lets an
event-capable host stop polling `task_status`:

```ts
import { taskFinishedEvent } from "@upstash/mcp-toolkit/events";

const taskFinished = taskFinishedEvent(events);

export const tasks = createTaskLayer({ store, dispatcher, principal, onSettle: taskFinished.onSettle });
```

It fires once when a task completes, fails or is cancelled. It is a personal event, emitted `to` the
task's owner, so only their subscriptions get it. We haven't tested it with ChatGPT yet. A host subscribes with no arguments for every task, or with `taskId` for one. The
payload includes the result when it fits in the 256 KiB envelope.

## Security

- **Callback URLs** must be `https` on a public host. `localhost`, `.local` and `.internal` names
  (trailing dots included), private, link-local, reserved and documentation IPs (also when embedded
  in IPv6), and credentials in the URL are refused, and redirects are never followed. The checks don't
  resolve DNS, so add egress filtering in production.
- **Verification:** a subscription is stored only after the callback echoes a signed challenge.
  Every failure returns the same error `-32015`, so a subscriber can't probe your network; the
  detail goes to your server logs.
- **Secrets** are stored encrypted with `MCP_EVENTS_SECRET_KEY`. A refresh with the same secret
  skips the challenge; a new secret verifies again.
- **Authorization:** `authorize` runs on every subscribe and refresh, and again before every
  delivery.
- **Delivery endpoint:** verifies QStash's signature with the `QSTASH_*_SIGNING_KEY` variables (or
  a `receiver` you pass). Without them it throws on the first request; it never sends unverified
  deliveries.

<Warning>
  `allowInsecureCallbacks: true` accepts `http://` and private addresses. Use it only for local
  development, never in production.
</Warning>

## Host responses

| Callback answers | What happens |
| --- | --- |
| `2xx` | Delivered. |
| `410 Gone` | The subscription is deleted. |
| `413`, or a redirect | The event is dropped, not retried. |
| Anything else, or no answer | QStash retries with backoff. |

## Options

**`createEventLayer`**

| Option | Default | |
| --- | --- | --- |
| `store` | required | `RedisSubscriptionStore`, or your own `SubscriptionStore` |
| `delivery` | required | `QStashDelivery`, or your own `EventDelivery` |
| `principal` | required | `({ auth, request }) => id \| { id, context } \| undefined`, may be async. The subscriber; `undefined` refuses. |
| `secretKey` | `MCP_EVENTS_SECRET_KEY` | Encrypts stored signing secrets. Required, with no built-in default. |
| `defaults.ttlMs` | 7 days | Lifetime granted when the host doesn't ask for one |
| `defaults.maxTtlMs` | 30 days | The most the server grants |
| `allowInsecureCallbacks` | `false` | Local development only |
| `timeoutMs` | 10 seconds | Timeout for each POST to a callback |

**`define` config:** `description`, `payload` and `authorize` (required), plus optional `title`,
`input`, `personal` and `match`.

**`QStashDelivery`:** `url` (required), `retries` (default 3), `retryDelay`, `headers`, `qstash`,
`receiver`.

**`RedisSubscriptionStore`:** `redis`, `prefix` (default `mcp-events:`).

Poll and stream delivery modes and replay cursors from the draft aren't implemented.

## Example

The [MCP toolkit demo](https://github.com/upstash/agentkit/tree/main/examples/mcp-toolkit-demo)
includes Deploy Watch, an events-only server with a `deploy.finished` event filtered by
environment, plus a local receiver that verifies each signed delivery. We tested it end to end with
ChatGPT monitors. It needs `MCP_EVENTS_SECRET_KEY` set, and its deploy-report route is
unauthenticated so the demo is easy to drive; a real server must authenticate the code that emits.
