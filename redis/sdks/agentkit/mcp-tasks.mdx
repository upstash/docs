An MCP tool call is a request that waits for its response. When the work takes minutes, something
gives up first: the client's tool timeout, your serverless function's limit, or the model.

`@upstash/mcp-toolkit/tasks` turns a slow tool into a task. The tool answers immediately with a task id, the
work runs on [QStash](/qstash/overall/getstarted) or [Upstash Workflow](/workflow/getstarted) so it
survives restarts and the client's tool timeout, and the task record lives in Upstash Redis. The model checks on it
with a shared `task_status` tool and can stop it with `task_cancel`.

These are ordinary MCP tools, so they work in every client today: Claude Code, Codex, Cursor,
OpenCode and ChatGPT. No client capability is required. The toolkit sits on top of the official MCP
TypeScript SDK and uses WebCrypto only, so it runs on Node and edge runtimes.

```bash
npm install @upstash/mcp-toolkit @modelcontextprotocol/server @upstash/redis @upstash/qstash zod
```

## Quickstart

Three files in a Next.js app.

### 1. Define the task layer, the task and the server

```ts lib/tasks.ts
import { McpServer } from "@modelcontextprotocol/server";
import { createTaskLayer } from "@upstash/mcp-toolkit/tasks";
import { QStashDispatcher, RedisTaskStore } from "@upstash/mcp-toolkit/tasks/upstash";
import * as z from "zod";

// Where the task record lives, how the work is delivered, and who is calling.
export const tasks = createTaskLayer({
  store: new RedisTaskStore(),
  dispatcher: new QStashDispatcher({ url: `${process.env.APP_URL}/api/execute` }),
  principal: ({ auth }) => auth?.extra?.userId as string | undefined,
});

// Defined at module scope, so every instance knows the handler, including
// an /api/execute instance that never serves an MCP request.
tasks.define(
  "generate_report",
  {
    description: "Generates a report on a topic.",
    inputSchema: z.object({ topic: z.string() }),
  },
  // The handler: your long-running work. It runs later, in /api/execute,
  // when QStash delivers the task — not inside the tool call.
  async ({ topic }, task) => {
    await task.update("Researching sources");
    const report = await writeReport(topic);
    return { content: [{ type: "text", text: report }] };
  },
);

// Called per request. Adds generate_report, task_status and task_cancel.
export function createServer() {
  const server = new McpServer({ name: "reports", version: "1.0.0" });
  tasks.register(server);
  return server;
}
```

`topic` is typed from `inputSchema`: Zod, Valibot and ArkType schemas all work. `principal` is
required, and `auth` is the verified token your route passes in; see [Users](#users).

### 2. Serve the MCP endpoint

```ts app/api/mcp/route.ts
import { createMcpHandler } from "@modelcontextprotocol/server";
import { createServer } from "../../../lib/tasks";

const mcp = createMcpHandler(() => createServer());

export const POST = (request: Request) => mcp.fetch(request);
```

The task layer only registers tools, so this is the SDK's own handler, unchanged. It works the same
with [`mcp-handler`](https://www.npmjs.com/package/mcp-handler) or any transport.

### 3. Add the execute endpoint

```ts app/api/execute/route.ts
import { tasks } from "../../../lib/tasks";

export const POST = tasks.createExecuteHandler();
```

This is where QStash delivers each task. The handler it returns verifies the QStash signature, finds
the task's handler, runs it and stores the result. It answers `200` when done and `500` to ask QStash
for a retry. A bad signature or body gets `489` with `Upstash-NonRetryable-Error: true`, since QStash
retries every other non-2xx.

The signing keys are required. Without `QSTASH_CURRENT_SIGNING_KEY` and `QSTASH_NEXT_SIGNING_KEY`
(or a `receiver` you pass), the endpoint throws on its first request instead of running unverified
deliveries. The same applies to `WorkflowDispatcher`.

### Environment variables

```bash .env
UPSTASH_REDIS_REST_URL=...

```

## What the model sees

1. It calls `generate_report({ topic })` and gets back a `taskId`, `status: "working"`, and a line
   telling it to call `task_status` in about two seconds.
2. `task_status({ taskId })` returns progress while the task runs, for example
   `"Researching sources"`.
3. Once the task completes, `task_status` returns a one-line status followed by your handler's
   `content`.

`task_cancel({ taskId })` marks the task `cancelled` and stops any pending delivery. Each response
also carries the task object in `structuredContent`:

```json
{
  "taskId": "0e30…",
  "status": "working",
  "statusMessage": "Researching sources",
  "pollIntervalMs": 2000,
  "ttlMs": 300000
}
```

A task is `working`, `completed`, `failed` or `cancelled`. The last three are final.

## The handler's `task` argument

| Member | What it does |
| --- | --- |
| `task.taskId` | The id of the running task. |
| `task.update(message)` | Writes a progress line. The model sees it on its next `task_status`. |
| `task.isCancelled()` | `true` once `task_cancel` was called, or the task expired. |

Cancellation is cooperative: your code keeps running until it checks. Check between steps:

```ts
async ({ sources }, task) => {
  for (const source of sources) {
    if (await task.isCancelled()) return {};
    await task.update(`Reading ${source}`);
    await read(source);
  }
  return { content: [{ type: "text", text: "Done" }] };
};
```

<Warning>
  Arguments are validated when the tool is called, then stored as JSON and handed to the handler
  later. Values that don't survive JSON, such as a `Date` produced by `z.coerce.date()`, arrive as
  strings. Keep task schemas to plain values, or parse them again inside the handler.
</Warning>

## Users

`principal` is required. It maps each call to a stable caller id, usually your user id. Each task
records who started it, and `task_status` / `task_cancel` only answer for that caller. Another
user's task id reads like an unknown one.

`principal` receives `{ auth, request }` and may be async.

### `auth`: the verified token

`auth` is the MCP SDK's `AuthInfo`:

```ts
interface AuthInfo {
  token: string;
  clientId: string; // the OAuth app, e.g. one id for every ChatGPT user
  scopes: string[];
  expiresAt?: number;
  extra?: Record<string, unknown>; // free-form, filled by your verifier
}
```

The SDK never fills it in from request headers. Your MCP route does, after verifying the bearer
token with your OAuth provider, by passing it to the handler:

```ts app/api/mcp/route.ts
import { createMcpHandler } from "@modelcontextprotocol/server";
import { createServer } from "../../../lib/tasks";

const mcp = createMcpHandler(() => createServer());

export async function POST(request: Request) {
  // Verify the bearer token with Clerk, WorkOS, Auth0 or your own auth server.
  const authInfo = await verifyToken(request);
  if (!authInfo) return new Response("Unauthorized", { status: 401 });
  return mcp.fetch(request, { authInfo });
}
```

Put the user id in `extra` when you build `authInfo`, and read it back in `principal`:

```ts
principal: ({ auth }) => auth?.extra?.userId as string | undefined,
```

Because the token was already checked, this is the path to prefer. Key on the user, not
`auth.clientId`: the client id identifies the OAuth app, which can be one id shared by every user of
a host like ChatGPT.

### `request`: the raw HTTP request

Apps that authenticate with a cookie or a session, rather than building an `AuthInfo`, can read the
request instead:

```ts
principal: async ({ request }) => (await getSession(request))?.userId,
```

The request is unverified. Check the session yourself, and never trust a header like `x-user-id`
that the caller can set.

### No anonymous mode

When `principal` returns `undefined`, the tool call is refused with "Not authenticated". A server
with no users of its own passes `principal: () => "local"`.

<Note>
  Task arguments and results are stored in Redis as plain JSON for the task's `ttlMs`, which is
  forever with `ttlMs: null`. Keep secrets out of them, or use a short TTL.
</Note>

## Retries without duplicates

Agents retry tool calls, especially ones that seemed to time out. With `idempotencyKey`, a second call
from the same caller with the same key returns the existing task instead of starting another:

```ts
tasks.define(
  "generate_report",
  {
    description: "Generates a report on a topic.",
    inputSchema: z.object({ topic: z.string() }),
    idempotencyKey: ({ topic }) => topic,
  },
  handler,
);
```

Keys are scoped by caller and tool, and last as long as the task is kept (`ttlMs`).

## Work longer than one function invocation

A QStash delivery is one serverless invocation, so the handler has to finish within your platform's
function limit. If it is killed, QStash redelivers and the handler starts over.

For longer work, use `WorkflowDispatcher`. Each step runs as its own invocation, and finished steps
are replayed from a journal instead of re-run. Three things change:

```ts lib/tasks.ts
import { RedisTaskStore, WorkflowDispatcher } from "@upstash/mcp-toolkit/tasks/upstash";
import type { WorkflowContext } from "@upstash/workflow";

export const tasks = createTaskLayer<WorkflowContext>({ // 1. the type argument
  store: new RedisTaskStore(),
  dispatcher: new WorkflowDispatcher({ url: `${process.env.APP_URL}/api/execute` }),
  principal: ({ auth }) => auth?.extra?.userId as string | undefined,
  // 3. a TTL longer than the work. It runs from creation and is never extended; once it passes,
  // the record is gone and isCancelled() returns true.
  defaults: { ttlMs: 60 * 60 * 1000 },
});
```

2. The work goes inside `task.run(...)` steps. The handler's `task` has the Workflow API, such as
`task.run`, `task.sleep` and `task.call`:

```ts
async ({ topic }, task) => {
  const sources = await task.run("fetch", () => fetchSources(topic));
  const report = await task.run("write", () => writeReport(sources));
  return { content: [{ type: "text", text: report }] };
};
```

Put side effects inside `task.run`. Code outside a step runs again on every invocation, and each
step is still one invocation, so keep every step within your function limit.

| | `QStashDispatcher` | `WorkflowDispatcher` |
| --- | --- | --- |
| Survives a crash | Yes, redelivered | Yes, replayed |
| Outlives one invocation | No | Yes, one invocation per step |
| On retry | Starts the handler over | Resumes from the last finished step |

## Options

**`createTaskLayer`**

| Option | Default | |
| --- | --- | --- |
| `store` | required | `RedisTaskStore`, or your own `TaskStore` |
| `dispatcher` | required | `QStashDispatcher`, `WorkflowDispatcher`, or your own `TaskDispatcher` |
| `principal` | required | `({ auth, request }) => string \| undefined`, may be async. The caller's id; `undefined` refuses the call. |
| `defaults.ttlMs` | 5 minutes | How long a task is kept. `null` keeps it forever. |
| `defaults.pollIntervalMs` | 2 seconds | Poll interval suggested to the model |
| `toolNames` | `task_status`, `task_cancel` | Rename the two shared tools |
| `onSettle` | none | `(task) => void`. Called once when a task completes, fails or is cancelled. |

**`tasks.define(name, config, handler)` config:** `description` and `inputSchema`, plus optional `title`, `ttlMs`,
`pollIntervalMs`, `queuedMessage`, `completedMessage` and `idempotencyKey`.

## Push instead of poll

A host that supports MCP Events can get a webhook when a task finishes instead of polling. Wire the
`task.finished` event from [MCP Events](/redis/sdks/agentkit/mcp-events) into `onSettle`; it fires to
the task's owner only:

```ts lib/tasks.ts
import { taskFinishedEvent } from "@upstash/mcp-toolkit/events";
import { events } from "./events"; // your event layer

const taskFinished = taskFinishedEvent(events);

export const tasks = createTaskLayer({
  store: new RedisTaskStore(),
  dispatcher: new QStashDispatcher({ url: `${process.env.APP_URL}/api/execute` }),
  principal: ({ auth }) => auth?.extra?.userId as string | undefined,
  onSettle: taskFinished.onSettle,
});
```

## Why tools, not the Tasks extension?

The 2026-07-28 MCP specification defines a [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)
where the *client* polls `tasks/get`, so the model spends no turns waiting. It is the right long-term
shape, but a server may only return a task to a client that declares the extension, and the clients
people use don't yet. Plain tools work everywhere today.

The task record already has the extension's shape, so a native adapter can serve the same records
once clients support it.
